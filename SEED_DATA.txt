 HOW TO LOAD
-----------
   mysql -u aj -p ez_simbs < ez_simbs_seed_data.sql

 The script is NOT idempotent (plain INSERTs). Running it twice will fail on
 the primary keys. To re-seed cleanly, run the commented "REMOVE SEED DATA"
 block at the bottom of ez_simbs_seed_data.sql first - it deletes only ids
 1001-1020, never any pre-existing row.

 All seeded rows are verified by queries at the bottom of the SQL file. All of
 them currently return clean results (see VERIFICATION at the bottom).

 stock_logs CAVEAT (important)
   stock_logs has only 20 rows, one per movement type, so it is a REPRESENTATIVE
   SAMPLE of activity, not a full audit ledger. Do NOT expect
   SUM(in) - SUM(out) to equal inventory.qty. The movements cover:
     in, out, adjustment, damage, return, transfer
   plus manual_issue and sale_return reference types.
   Every 'in'/'out' row DOES reference a real document that actually contains
   that product at that quantity, and no movement exists for the held or
   cancelled sales - both are enforced by SQL checks #8 and #9.
   Notably: sale 1008 is HELD, so it correctly has no stock movement at all;
   the 'out' row near it points at sale 1009 instead.

 ================================================================================
  7b. RETURNS & REFUNDS  (Phase-13)
 ================================================================================

  Money always follows classes/SaleReturn.php: a return is a document that
  references a sale (POS) or an order (online) and never mutates source totals.
  The reversed shares discount/tax/shipping are stored on the return itself, so
   refund_total = subtotal - discount + tax + shipping holds EXACTLY, and every
  refund is capped (refunds may never exceed what the source took in).

  RETURN STATUS SPLIT  (20 rows, every status represented)
    refunded  12: 1001 1002 1006 1007 1008 1009 1010 1011 1012 1015 1017 1020
    requested  4: 1004 1005 1013 1019
    rejected   2: 1003 1014
    approved   1: 1016          (waiting in the bin, nothing received yet)
    cancelled  1: 1018          (VOIDED as a duplicate entry)

  SCENARIO GUIDE  (use these in the returns screen)
    POS immediate refund (loss):  1001  soft drinks, lids dented -> restock 0,
      credit note written off. 214.50 back, 21 loyalty points clawed back.
    POS partial qty refund:       1002  half-consumed Pepsi pack returned; only
      1 of 5 units comes back. 66.00 refunded, 6 points clawed back.
    POS needs-approval refund:    1016  approved but not yet received - use the
      Receive button next, then Refund.
    POS voided/cancelled:         1018  wrong return keyed in error, VOIDED; its
      sale line tally reverted to 0 (sale 1018 still shows completed).
    POS restock vs write-off:     1011  3 crates back; 2 sellable (2 stock_logs
      restock rows), 1 damaged (no restock). Follow on product 1011 in
      Inventory -> stock history.
    POS damaged-no-restock:       1017, 1009, 1007, 1012 (single unit back).
    POS ceiling clamp (2 refunds on one sale):
      Sale 1020 (715.00) has refund 1008 (476.67) AND refund 1020 (238.33);
      the second refund stops exactly at the remaining 238.33 - SQL check #15b.
    Online requested (no admin yet):  1004, 1005, 1013, 1019 - use the Approve /
      Reject buttons; 1019 is the photo case (5 evidence photos uploaded).
    Online rejected:              1003  customer never returned goods;
      1014  damaged at delivery, refund declined, replacement issued. Both carry
      an admin_note you can read in the view screen.

      832.15 back to the original card (REFMOB/REFCARD rows).

  CUSTOMER/REQUESTER MAPPING
    requesters are storefront users 1005/1016 (they made the original orders);
    online returns resolve their customer through orders.customer_id (1001 has
    three orders -> three returns; the other online returns record NULL walk-in
    customers exactly like their orders do).
    POS returns are raised and approved by the counter staff user 10 and carry
    requested_by = approved_by = 10 for a complete audit timeline.
    Admin approvals/rejections are recorded as user 1 (seed.admin@).

  PAYMENTS LEDGER (sale_return_payments, 12 rows - only REFUNDED returns pay)
    The 8 outstanding returns (requested/approved/rejected/cancelled) have no
    refund row on purpose. Methods match the original tender: cash refunds out
    of the till, card/mobile refunds carry REFCARD-*/REFMOB-* reference codes.
    Refund money never re-enters sale_payments - section 6 explains why the
    returned sales keep their original paid figures.

  LOYALTY CLAW-BACKS
    A POS refund reverses loyalty in step: 1001->21, 1002->6, 1006->52,
    1007->16, 1008->47, 1009->31, 1010->63, 1011->55, 1012->3, 1017->27,
    1020->23. Online refunds (1003-1005, 1013-1015, 1019) reverse nothing -
    online sales earn no points. The value is floor(grand_total/10) scaled by
    refund_total/grand_total; 0 when the refund is under the points threshold.

  STOCK
    Receive() decides restock: sellable units get a stock_logs 'sale_return'
    row (1018, 1021-1023); damaged units get none. Check #16 aggregates these
    per (return, product) and must return zero mismatches.

 REMOVING THE SEED DATA
   Uncomment and run the REMOVE SEED DATA block at the bottom of
   ez_simbs_seed_data.sql. It deletes the return tables first (photos,
   payments, items, headers - both sale and purchase), then the rest, in
   FK-safe order, and never touches pre-existing rows. stock_logs is cleared
   through 1041 (the Phase-13 restocks 1021-1023 plus the Phase-14 return
   rows 1024-1041), sale_items through 1022, and return_photos through 1023.
   It does not delete the seed SVG images. On a DB that was already seeded
   once, run this block before loading the file again. The seed file is a
   text fixture, so REMOVE + re-import regenerates returned_qty and
   suppliers.balance from the extended INSERTs automatically.
